## 2. Dependency Ordering — Verification Method & Findings

**[STRONGLY INFERRED]** — no citation to `18` §2 exists anywhere in the package, so this section introduces no numbering conflict. It exists to make §1's phase assignments independently checkable rather than asserted.

**Method:** every one of the 91 Jira stories with an `Original key` was parsed for its `Dependencies` field; a topological depth was computed by following each dependency chain to its root (stories with no dependencies = depth 0). Soft dependencies (marked "(soft dep)" in the backlog, e.g. `SCH-006`'s soft dependency on `RESC-007`, `SCH-009`'s on `ANLY-004`, `ROAD-005`'s on `MEM-001`) were treated as non-blocking, matching `03` §5's own finding: "Every 'soft dep'... correctly matches a case where `18`'s phased plan builds the dependent story before the dependency lands, using an explicit stub — this is intentional, not an oversight." `SCH-006` and `SCH-009` accordingly ship in Phase 3 with a stubbed risk flag / stubbed historical-calibration value, filled in properly once `RESC-007` (Phase 6) and `ANLY-004` (Phase 6) land — this is not a violation of dependency order, it is the walking-skeleton philosophy (Phase 0's own method) applied again at smaller scale within Phase 3.

**Findings confirming `03` §5's own flagged ordering risk:** `SEC-001` ("Authorization/user-scoping audit") depends on "All API stories" and `OPS-004` ("Full test suite completion") depends on "All stories" — both are correctly Phase 7 (last), which `03` §5 already noted means user-scoping is only *audited* at the end, not verified incrementally. This plan does not resolve that risk (it isn't this document's to resolve), but does confirm `03` §5's own recommendation should be read as this document's actual per-feature practice: `18` §3's Definition of Done below requires "security requirements met... user-scoping verified" per feature, in every phase, with `SEC-001` serving as a final sweep rather than the only check — exactly as `03` §5 recommended.

**No contradiction found** between the computed topological order and the phase-content citations gathered for §1 above — every hard citation to a specific phase's contents (Phase 0, 3, 4, 5, 6, 7) is satisfied by a set of stories whose actual dependency depths cluster together, which is the evidence that the correction brief's original informal summary ("Foundation → Domain → Event Log → Scheduling → Execution → Recovery → remaining UI/product systems → AI/analytics/memory → Security/Operations") needed exactly one correction: **AI (Phase 4) comes before Execution/Recovery (Phase 5), not after** — `EXEC-001` topologically depends on `SCH-015`, which itself is only completed once `EVT-002` (Phase 4) exists, and the Master Spec's own "Atlas works without AI first" framing describes AI as bolting onto an already-working deterministic core, which only makes sense if AI (Phase 4) is built and tested for failure-tolerance *before* the parts of the system (Execution, Recovery) that must keep working when AI fails.

## 3. Definition of Done

**[EXPLICIT]** — this is the section every one of the following citations points to by number: `16` §3 ("`18` §3's requirement that 'input validation matches the API contract'"), `16` §5 ("required by `18` §3 naming 'state-machine' as one of the four category examples"), `16` §7 ("`18` §1 Phase 0's own exit criterion... every phase in `18` builds toward... Phase 2's exit criterion"), `17` (CI as "a hard merge gate... consistent with `18` §3's Definition of Done requiring 'CI green, migrations applied cleanly, no regression in the existing test suite' for every feature in every phase"), `03` §5 ("`18` §3 already requires 'Security requirements met... user-scoping verified' per feature").

A story is Done when, and only when, **all** of the following hold:

1. **Acceptance criteria met** exactly as stated in the Jira story (or as amended per an approved `JIRA_CHANGE_PROPOSALS.md` entry).
2. **Input validation matches the API contract** (`12_API_SPECIFICATION.md`) — request/response shape, error shape, user-scoping.
3. **Relevant test categories from `16_TEST_STRATEGY.md` pass** — at minimum unit and integration, plus the specific category that applies (scheduling/determinism, rescheduling/state-machine, or AI-contract, per which of `16`'s categories the story touches).
4. **CI green, migrations applied cleanly, no regression in the existing test suite** — verified for every feature, in every phase, not deferred to a project-end sweep.
5. **Security requirements met, including user-scoping verified** for any story touching an API endpoint or state-bearing table — per-feature, with `SEC-001` (Phase 7) as a final audit sweep, not the only check (§2 above).
6. **Event Log coverage** — any state transition the story introduces has a corresponding `10_EVENT_LOG.md` event type (existing or newly reused per this pass's own reuse-over-proliferation principle, `10` §2) and that event is actually written inside the same transaction as the state change (`13` §1's transaction-boundary rule).
