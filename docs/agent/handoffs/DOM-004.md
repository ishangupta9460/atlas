## DATABASE CHANGES

- V6 creates `recurring_intentions` with FKs to `users` and nullable `goals`, a positive weekly target, non-negative current-week remaining count, flexibility-tier check, and indexes on user/goal IDs.
- `category_id` is a nullable plain `BIGINT`, deliberately without a foreign key because `categories` is owned by future DOM-005. Creation with an arbitrary category ID is covered by integration tests, proving no phantom FK blocks migration/use.
- `current_week_remaining_count` is mutable state on the entity row. It initializes from `target_count_per_week`, decrements only on completion (floor zero), and resets to the full target each new week. No historical instances table was invented because none is specified.
- Fresh H2 Flyway application was exercised by the Spring integration suite. Production MySQL migration has not been run locally because no MySQL service is configured in this workspace.

## API CHANGES

- Added `POST /recurring-intentions`, `GET /recurring-intentions/{id}`, and `PATCH /recurring-intentions/{id}/target` as defined by `12` §5.
- Added `POST /recurring-intentions/{id}/instances/complete` to report the required completion action, plus `POST /recurring-intentions/{id}/instances/miss` for explicit miss reporting.
- `12_API_SPECIFICATION.md` was intentionally not changed. Its §5 has no route for the required instance-completion/miss actions; this is an API-surface gap to resolve through the normal product/API decision process.
- Target updates affect only the next weekly reset; they do not retroactively change this week's remaining count. Collaborative confirmation for Atlas-suggested changes remains out of scope until that tier system exists.

## EVENT LOGGING DECISION

- Event logging is required here, unlike DOM-002. `01_SYSTEM_ARCHITECTURE.md` §4 and `13_DATABASE_SPECIFICATION.md` §4 explicitly include `recurring_intentions`, and `02` §2.5 names `recurring_intention.reset`, `recurring_intention.instance_completed`, and `recurring_intention.instance_missed`.
- Reset is recorded as `atlas` with a populated reason; user-reported completion/miss use actor `user`. A real DB constraint test proves an Event insert failure rolls back the paired completion count mutation.

## INDEPENDENT REVIEW — 2026-09-13

**VERDICT: FAIL**

### Blocking finding

- `RecurringIntentionService.create` and `RecurringIntentionService.updateTarget` each mutate `recurring_intentions` inside a transaction without writing a corresponding Event Log row. This violates `01_SYSTEM_ARCHITECTURE.md` §4 and `13_DATABASE_SPECIFICATION.md` §4, which apply to every meaningful recurring-intention state change. `02` §2.5 supplies the three cycle-action event types but does not settle event types for creation or target change; do not invent those names without the required product/architecture decision. Resolve that contract and make both writes atomic with their events before merge.

### Required test additions

- Add a creation test in which the authenticated user submits a `goalId` owned by another user and receives the expected 404. The service appears to enforce this through `existsByIdAndUserId`, but the required cross-user creation case is presently untested.
- Add direct coverage that reset replaces an anomalously above-target remaining count, rather than merely adding target. The implementation assignment is correct by inspection, but the existing test reaches only partial and zero prior values.

### Review evidence

- The five routes derive the caller from `@AuthenticationPrincipal`; fetch, target-update, complete, and miss use `findByIdAndUserId`. Creation validates a supplied goal belongs to that JWT user.
- The weekly behavior correctly uses assignment on reset, `Math.max(0, remaining - 1)` on completion, and no count mutation on miss. Completion beyond zero and an unchanged miss are tested.
- All three cycle events, actor attribution, and reset reason are implemented. `RecurringIntentionTransactionIntegrationTest` installs a real H2 check constraint that rejects the Event insert, then directly queries both the retained count and absent event after rollback.
- V6 applied through the fresh H2 MySQL-mode integration suite. SQL uses MySQL-compatible `AUTO_INCREMENT`, `DATETIME(6)`, checks, and indexes; `category_id` is intentionally nullable with no FK, appropriate until DOM-005.
- No Category/Tag entity, categories FK, scheduler, Goal Risk, Commitment, or Task code was introduced. The additive `GoalRepository.existsByIdAndUserId` method is necessary for goal-link ownership validation and did not regress DOM-001.
- `12_API_SPECIFICATION.md` is untouched; the two additive completion/miss routes leave its documented API gap explicitly recorded.
- The DOM-004 work is still uncommitted in the working tree, so there was no actual DOM-004 commit hash to inspect with `git show`.
