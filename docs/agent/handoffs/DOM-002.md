## DATABASE CHANGES

- V5 creates `roadmaps(id, goal_id, source, created_at)` with a non-null Goal FK, `user_interview`/`imported` check constraint, Goal index, and unique `goal_id`. The unique key implements `02` §1.1's “has one Roadmap (optional)” relationship.
- V5 creates `milestones(id, roadmap_id, title, display_order)` with a non-null Roadmap FK and `(roadmap_id, display_order)` index. The physical column is `display_order`, rather than SQL-reserved `order`; API payloads/responses retain `order`.
- No destructive migration or cascade deletion was added. Fresh H2/MySQL-mode Flyway application passed as part of the integration/full suites.

## API CHANGES

- `POST /goals/{goalId}/roadmaps` — create a Roadmap under the caller-owned Goal; source defaults to `user_interview`, with `imported` accepted as entity-layer data only.
- `GET /roadmaps/{id}` — fetch caller-owned Roadmap with its ordered Milestones.
- `PATCH /roadmaps/{id}` — returns `409 ROADMAP_IMMUTABLE`; source is immutable and no other Roadmap field is specified as mutable.
- `POST /roadmaps/{roadmapId}/milestones`, `GET /milestones/{id}`, `PATCH /milestones/{id}` — Milestone CRUD surface for create/read/title-order update.
- `12_API_SPECIFICATION.md` was deliberately not edited. It contains import-pipeline routes but no direct entity CRUD contract for this DOM story; this API-surface gap requires a documented decision before specification changes.

## EVENT LOGGING DECISION

- No Event Log writes were added. `01_SYSTEM_ARCHITECTURE.md` §4 and `13_DATABASE_SPECIFICATION.md` §4 explicitly require paired events for meaningful writes to `commitments`, `goals`, `scheduled_blocks`, and `recurring_intentions`; Roadmaps and Milestones are absent. `02` §1.2–1.3 defines both as non-schedulable structural/grouping entities without state machines. Adding event logging would therefore invent a requirement.
