## DATABASE CHANGES

- V7 creates `categories(id, user_id, name, default_flexibility_tier, color, created_at)`, with a non-null User FK, no invented per-user name uniqueness constraint, a lower-case flexibility-tier check matching DOM-004's established persisted/request representation, and an index on `user_id`.
- `created_at` is a minor consistency addition: it is not listed in `02` §1.9 but is consistently present on current entities.
- The current DOM-004 implementation has no enum class despite its tier validation. To avoid an out-of-scope persistence/API refactor, Category uses the same constrained lower-case String representation rather than extracting a shared enum; no DOM-004 tier behavior changed.
- V7 adds `fk_recurring_intentions_category` by `ALTER TABLE`, leaving V6 immutable. The nullable FK defaults to restrictive deletion; the service detects references first and produces `409 CATEGORY_IN_USE` rather than a database exception. This preserves referenced intentions and avoids inventing cascade or set-null behavior.
- Fresh H2 MySQL-mode Flyway output applied all seven migrations through V7 successfully.

## API CHANGES

- `POST /categories`, `GET /categories`, `GET /categories/{id}`, `PATCH /categories/{id}`, and `DELETE /categories/{id}`; all derive the owner exclusively from JWT.
- Both list and single fetch are provided: list is the primary set-oriented use case from `02` §1.9, while fetch maintains the direct-entity consistency used by existing APIs.
- `12_API_SPECIFICATION.md` was deliberately not changed. It was read end to end and has no Category/Tag section or route, an API-surface gap to be formalized by the product/API owner.

## EVENT LOGGING DECISION

- No Category Event Log writes were added. Re-derived from `01` §4, `13` §4, and `10` §5: the atomic event rule applies to meaningful schedule, progress, lifecycle, planning, or work-state changes in the named `commitments`, `goals`, `scheduled_blocks`, and `recurring_intentions` tables. Category is absent from that list, has no state machine in `02` §2, and is a flat structural/configuration lookup entity. Adding events would invent an unsupported contract.
